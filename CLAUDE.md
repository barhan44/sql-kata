# CLAUDE.md — правила работы над SQL Kata

## 1. Миссия проекта

`sql-kata` — воспроизводимый тренажёр по PostgreSQL для инженеров данных и
backend-разработчиков. Каждая ката проверяет не текст запроса, а его результат
на реальной базе PostgreSQL 16+, поднятой в Testcontainers.

Главные свойства, которые нельзя ломать:

1. **Один контейнер PostgreSQL на JVM.** Схема загружается один раз.
2. **Изоляция изменений.** Кандидат и эталон выполняются в транзакциях с
   гарантированным `ROLLBACK`.
3. **Строгая детерминированная проверка.** Имена и типы колонок, значения и
   порядок строк. В каждом задании должен быть явный `ORDER BY`.
4. **Понятная диагностика.** При ошибке выводится первое расхождение и
   ограниченный срез эталонных/фактических строк.
5. **Русские условия и `@DisplayName`.** SQL-условия, комментарии решений и
   отображаемые имена тестов — на русском. Идентификаторы в коде и SQL — на
   английском.

## 2. Стек и инфраструктура

- Java 21, Maven.
- PostgreSQL 16 (`postgres:16-alpine`).
- JUnit Jupiter, AssertJ, Testcontainers, PostgreSQL JDBC, slf4j-simple.
- Testcontainers `2.0.5`. В 2.x модули называются
  `org.testcontainers:testcontainers-postgresql` и
  `org.testcontainers:testcontainers-junit-jupiter`. Это осознанное решение:
  Docker Engine 29+ требует API ≥ 1.40, а docker-java ветки 1.x по умолчанию
  уходит на старый API. Не понижать версию без проверки на Docker 29+.
- Базовый класс: `src/test/java/dev/sqlkata/AbstractSqlKataTest.java`.
  В нём единственный статический `PostgreSQLContainer`. Не добавлять второй
  контейнер и не менять `forkCount=1`/`reuseForks=true` без пересмотра модели
  синглтона.
- Движок: `src/test/java/dev/sqlkata/SqlKataVerifier.java`.
  Ослаблять сравнение ради прохождения конкретной каты запрещено. Исправлять
  нужно запрос или контракт задания.

## 3. Структура файлов

```
src/main/resources/
  schema/01_init_schema.sql
  katas/<level>/kata_XXX_<snake_case>.sql
  solutions/<level>/kata_XXX_<snake_case>.sql
src/test/java/dev/sqlkata/
  AbstractSqlKataTest.java
  SqlKataVerifier.java
  <level>/KataXXX_<PascalCase>Test.java
```

Уровни и их Java-пакеты:

| Каталог ресурсов | Пакет тестов | Диапазон номеров |
|---|---|---|
| `01_junior` | `dev.sqlkata.junior` | 001–025 |
| `02_middle` | `dev.sqlkata.middle` | 026–055 |
| `03_senior` | `dev.sqlkata.senior` | 056–075 |
| `04_pro_tuning` | `dev.sqlkata.tuning` | 076–090 |

Номера непрерывны и не переиспользуются. Следующая ката продолжает последний
номер предыдущего уровня.

## 4. Контракт одной каты

### 4.1. Файл задания

Путь: `src/main/resources/katas/<level>/kata_XXX_<slug>.sql`.

Обязательное содержимое:

- русский бизнес-контекст;
- перечень используемых таблиц и ключевых колонок;
- точный список выходных колонок **по порядку** и их PostgreSQL-типы;
- правила сортировки, включая tie-breaker;
- правила обработки `NULL`;
- ограничения (`LIMIT` только если он нужен бизнес-задаче);
- подсказка об основном приёме уровня;
- напоминание, что сравнивается порядок строк;
- заглушка ровно одна команда:

```sql
SELECT 1 WHERE FALSE;
```

Нельзя добавлять в заглушку корректные колонки: стартовый тест должен падать
из-за отсутствия результата и понятного diff.

### 4.2. Эталонное решение

Путь: `src/main/resources/solutions/<level>/kata_XXX_<slug>.sql`.

Требования:

- идиоматичный PostgreSQL 16+;
- один запрос/команда, завершающийся точкой с запятой;
- русские комментарии: почему выбран приём, что с `NULL`, где важна
  производительность и индексы;
- не использовать `random()`, `now()`, `current_date` и другие
  недетерминированные источники без фиксации значения;
- все вычисляемые колонки должны иметь явные псевдонимы;
- типы должны совпадать с контрактом; при необходимости использовать `CAST`;
- сортировка строго детерминирована;
- нельзя полагаться на физический порядок строк;
- для `UPDATE`/`DELETE`/`INSERT ... RETURNING` предпочтителен `RETURNING`,
  потому что верификатор умеет сравнивать его `ResultSet`; без `RETURNING`
  сравнивается только число изменённых строк.

### 4.3. Тест

Путь: `src/test/java/dev/sqlkata/<package>/KataXXX_<PascalCase>Test.java`.

Шаблон:

```java
package dev.sqlkata.junior;

import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

import dev.sqlkata.AbstractSqlKataTest;

@DisplayName("Junior · Kata 001 — Краткое русское название")
class Kata001_ExampleTest extends AbstractSqlKataTest {

    @Test
    @DisplayName("что именно проверяет тест")
    void shouldExample() {
        assertKataMatches("katas/01_junior/kata_001_example.sql");
    }
}
```

Один тестовый метод на кату. @DisplayName на классе и методе — на русском.
Не дублировать ожидаемый результат в Java: единственный источник истины — SQL
в `solutions/`.

## 5. Правила авторинга SQL

- Целевая версия — PostgreSQL 16+. Не использовать MySQL/SQL Server синтаксис.
- Явно указывать псевдонимы таблиц при JOIN.
- Предпочитать SARGable-условия: не оборачивать индексируемые колонки в
  функции без необходимости.
- Для границ timestamp использовать полуинтервал `[from, to)`.
- При бизнес-датах не зависеть от `TimeZone` сессии: задавать зону явно через
  `AT TIME ZONE` или `timestamptz`-литерал со смещением.
- Денежные значения — `numeric`, не `float`/`double`.
- Деление защищать `NULLIF`, если знаменатель может быть нулевым.
- Для `IN`/`NOT IN` помнить о трёхзначной логике. Если в подзапросе возможен
  `NULL`, использовать `EXISTS`/`NOT EXISTS` и объяснять ловушку в условии.
- Для проверки отсутствия связи предпочитать anti-join или `NOT EXISTS`
  в зависимости от учебной цели.
- Проверять план не только «глазами»: при сомнениях — `EXPLAIN`, но не
  добавлять планы в проверяемый результат каты.
- Не использовать временные таблицы, DDL, `COMMIT`, `ROLLBACK`, `VACUUM`,
  `SET` внутри файла каты: контракт верификатора — одна изолированная команда.
- Имена временных CTE/подзапросов — английские, короткие и осмысленные.
- Не менять схему под конкретный запрос, если задачу можно решить честно.

## 6. Данные и схема

`src/main/resources/schema/01_init_schema.sql` — общий контракт всех уровней.

- Не изменять существующие seed-строки без полной ревизии всех открытых кат:
  эталонные запросы могут начать давать другой бизнес-результат, хотя
  self-сверка `-DuseSolution=true` этого не заметит.
- Допустимые изменения по умолчанию — **аддитивные**: новые таблицы, колонки
  с `DEFAULT`, индексы, новые строки, не влияющие на существующие выборки.
- Каждая новая таблица должна иметь PK, осмысленные FK, CHECK-ограничения и
  индексы под заявленные сценарии.
- В seed-данных должны быть граничные случаи: `NULL`, отсутствующие связи,
  дубликаты событий, возвраты, отмены, иерархии.
- Не «чистить» данные от аномалий: они — учебный материал.
- Если для уровня нужен большой объём, не раздувать общий seed. Делать
  отдельный load-сценарий/тестовый класс для tuning-кат и явно помечать его
  тегом, чтобы обычный прогон оставался быстрым.
- При любом изменении схемы или seed-данных обязательно запускать полный
  набор с эталонами и заново просматривать результаты затронутых кат.

## 7. Верификация: Definition of Done

Перед коммитом новой каты/волны:

```bash
# 1. Все эталоны должны пройти: 100% green
mvn test -DuseSolution=true

# 2. Обычный режим: все заглушки должны упасть с diff
mvn test
```

Для обычного `mvn test` допустим и ожидаем BUILD FAILURE: каждая заглушка
обязана упасть. Проверять, что число падений равно числу кат, а сообщения
содержат понятное расхождение, а не `NullPointerException`/ошибку движка.

Дополнительно:

- точечный прогон новой каты в обоих режимах;
- проверка, что контейнер стартовал один раз;
- проверка, что после прогона база не изменилась (транзакции откатываются);
- отсутствие случайных данных и недетерминированного порядка;
- отсутствие комментариев-заглушек вида TODO в эталоне.

## 8. Правила генерации волны 02_middle (026–055)

Цель: переход от «правильно выбрать» к «правильно преобразовать данные».

Обязательные темы (минимум по две каты на тему):

1. Оконные функции: `ROW_NUMBER`, `RANK`, `DENSE_RANK`, `LAG`, `LEAD`,
   `NTILE`, running total, скользящие окна и `ROWS`/`RANGE` frames.
2. CTE и рекурсивные CTE: дерево категорий, оргструктура, путь от листа к
   корню, обнаружение циклов.
3. JSONB: выборка вложенных значений, `jsonb_array_elements`, агрегация
   `jsonb_agg`, GIN-индексы, отличие `jsonb` от `json`.
4. Массивы: `unnest`, `ANY`, `array_agg`, пересечения тегов.
5. `LATERAL JOIN`, `JOIN ... ON` с агрегированными подзапросами.
6. Продвинутая агрегация: `GROUPING SETS`, `ROLLUP`, `CUBE`,
   `FILTER (WHERE ...)`, доли через оконные суммы.
7. Множества: `INTERSECT`, `EXCEPT`, корректное сравнение `UNION` и
   `UNION ALL` на дубликатах.
8. Даты и временные интервалы: когорты, серии, gaps and islands без
   генерации случайных данных.

Правила:

- условия остаются в тех же файлах `katas/02_middle/`;
- решения — в `solutions/02_middle/`;
- тесты — в `dev.sqlkata.middle`;
- каждая ката должна требовать понимания конкретного приёма, а не только
  синтаксиса;
- в решении объяснять, почему альтернативный приём хуже (например, окно vs
  коррелированный подзапрос на большом объёме);
- для всех задач с окнами фиксировать tie-breaker, иначе ранг нестабилен.

## 9. Правила генерации волны 03_senior (056–075)

Цель: сложные бизнес-инварианты, транзакционные сценарии и трудные
аналитические модели.

Темы:

- рекурсивные иерархии с путями, уровнями и защитой от циклов;
- temporal-запросы: SCD, интервалы действия, пересечения и gap detection;
- upsert (`INSERT ... ON CONFLICT`), `MERGE`;
- транзакции, уровни изоляции, конкурентные изменения, блокировки;
- аккуратные `UPDATE`/`DELETE` с `RETURNING` и ограничением набора строк;
- дедупликация событий, идемпотентность платежей;
- продвинутая аналитика: воронки, retention, когорты, взвешенные метрики;
- моделирование ограничений и инвариантов (CHECK/UNIQUE/EXCLUDE), когда это
  уместно.

Правила:

- задачи, которые через `assertKataMatches` не проверить (уровни изоляции,
  гонки, блокировки), выносятся в отдельный тестовый harness с несколькими
  соединениями; не притворяться, что однопроцессная проверка их покрывает;
- любые DML остаются в транзакции с откатом;
- результаты DML проверять через `RETURNING` — одного updateCount недостаточно;
- конкурирующие тесты должны иметь таймауты и детерминированное завершение;
- не использовать `pg_sleep` там, где можно проверить блокировку через
  `pg_locks`/таймаут.

## 10. Правила генерации волны 04_pro_tuning (076–090)

Цель: научить читать планы, проектировать индексы и доказывать улучшение.

Темы:

- `EXPLAIN`, `EXPLAIN (ANALYZE, BUFFERS)`, `EXPLAIN ... FORMAT JSON`;
- последовательное и индексное сканирование, bitmap scan;
- составные, частичные, covering-индексы (`INCLUDE`);
- селективность, кардинальность, статистика и `ANALYZE`;
- сортировки, хеш-агрегация, nested loop vs hash join;
- `LATERAL` и переписывание запросов;
- партиционирование и partition pruning;
- работа с большими объёмами, меры времени и буферов;
- `pg_stat_statements`/`pg_stat_user_tables` в объяснении, но не как
  обязательное расширение для теста;
- поиск и устранение антипаттернов.

Правила:

- обычные ката проверяют корректность результата; performance-ката проверяет
  **структурные свойства плана**, а не абсолютное время;
- не сравнивать миллисекунды как стабильный oracle: машины и Docker разные;
- для tuning-тестов допускается отдельный крупный набор данных, генерируемый
  детерминированно (`generate_series`) в отдельном контейнере/тестовом классе;
- проверять отсутствие `Seq Scan` по большой таблице, попадание в индекс,
  наличие pruning, уменьшение числа буферов — в зависимости от задания;
- каждое задание должно содержать бизнес-обоснование индекса и цену записи;
- performance-тесты помечать тегом (`@Tag("tuning")`) и документировать
  отдельную команду запуска;
- не добавлять тяжёлые данные в общий seed для Junior/Middle/Senior.

## 11. Стиль и коммуникация

- Комментарии и документация — на русском.
- Имена таблиц, колонок, CTE, Java-классов и методов — на английском.
- Форматирование SQL: ключевые слова заглавными, отступ 4 пробела,
  выровненные списки колонок; единый стиль внутри файла.
- Тексты ошибок верификатора должны объяснять, где и что не совпало.
- Коммиты осмысленные:
  - `feat(katas): add 026-055 middle wave`
  - `fix(verifier): compare null values without NPE`
  - `docs: document tuning rules`

## 12. Запрещено

- Подгонять эталон под неверный запрос ученика.
- Ослаблять сравнение типов/порядка строк, чтобы «все прошло».
- Добавлять правильный ответ в файл `katas/`.
- Делать заглушку, которая проходит проверку.
- Использовать `LIMIT` для маскировки неполного результата.
- Менять общий контейнер на контейнер на каждый тест.
- Использовать изменяемое системное время, `now()` и случайные значения в
  эталонных результатах.
- Коммитить `target/`, логи и локальные файлы IDE.
